# 레이아웃 적용 — 셀 일괄 쓰기(`POST /api/cells/bulk`) 와 PLC 반영

레이아웃 생성 규칙으로 만든 셀을 **레지스트리(로컬 사본)** 에 넣는 길과, 그것을 **PLC** 에 올리는 길을
적는다. 둘은 다른 단계다 — 적용은 콘솔 DB 만 바꾸고, 로봇이 쓰는 값이 되려면 PLC 쓰기까지 해야 한다.

## 왜 "추가"가 기본인가

처음에는 모드가 하나였다: 생성한 구역의 기존 셀을 **전부 지우고** 새로 깐다. 현장에서 더 잦은 일은
이미 깔려 쓰고 있는 칸은 그대로 두고 **빈 자리에만 더 까는** 것이었고, 한 번의 실수로 쓰던 구역이
통째로 사라지는 조작이 기본값이어서는 안 된다. 그래서 모드를 셋으로 나누고 기본을 **추가**로 두었다.

| 모드 (`mode=`) | 화면 | 지움 | id 중복 | 겹침 |
|---|---|---|---|---|
| `append` **(기본)** | 추가 | 없음 | 건너뜀(`auto_id=1` 이면 빈 id 로 옮김) | 건너뜀 |
| `replace_section` (+`replace_section=<1..3>`) | 구역 교체 | 그 구역에서 생성분이 같은 id 로 이어받지 않는 셀 | 덮어씀(경고) | 씀(경고) |
| `overwrite` | 덮어쓰기 | 없음 | 덮어씀(경고) | 씀(경고) |

`mode` 를 비우고 `replace_section=<n>` 만 주면 옛 규약대로 구역 교체다(옛 클라이언트 호환).
셀 그리드 편집기의 저장은 `mode=overwrite` 로 보낸다 — 거기서는 사람이 적은 값이 이겨야 한다.

## 충돌 판정 (서버가 정한다)

판정은 백엔드 `registry::bulk::plan` 이 한다. 화면(`lib/task/layoutGen.ts::previewApply`)이 같은 규칙으로
미리 보지만 창이 여럿이면 그 사이에 셀이 바뀔 수 있으므로, **적용 결과는 서버 응답이 진실**이다.

1. **값이 같은 줄** — 같은 id 의 기존 셀과 모든 필드가 같으면 `unchanged`(쓰지 않는다).
   PLC 에서 읽어 온 깨끗한 행을 괜히 "로컬 수정"으로 만들지 않기 위해서다.
2. **id 중복** — 남아 있는 기존 셀과 id 가 같을 때. `append` 는 건너뛰고(`auto_id=1` 이면 그 구역의
   마지막 id 다음 빈 번호로 옮겨 `remapped`), 나머지 모드는 덮어쓰며 경고만 낸다.
3. **겹침** — 중심 거리 < `지름 − 허용오차`. 지름은 요청의 `diameter` 파라미터, 없으면 **그 셀의
   `max(length, width)`**(슬롯은 length×width 로 저장되고 생성기는 둘 다 지름으로 채운다 — 다르면 큰 쪽이
   안전하다). 허용오차는 기본 0.5 mm(`tolerance=`), 좌표를 0.1 mm 로 반올림해 저장하기 때문이다.
   검사 상대는 **남는 기존 셀 + 이번 배치에서 이미 받아들인 줄**(배치 안끼리 겹치는 것도 잡는다).
   사유 문구에는 상대 id 와 중심 거리가 들어간다.

모든 줄은 **쓰기 전에** 전부 검증한다(`validate_cell` + 요청 안 id 중복) — 하나라도 틀리면 400 이고
아무것도 쓰지 않는다.

## 응답

```jsonc
{
  "mode": "append", "auto_id": false,
  "created": 12, "updated": 0, "unchanged": 3, "skipped": 2, "remapped": 1,
  "removed": 0, "total": 118,
  "rows": [ { "id": 101, "outcome": "skipped", "reason": "기존 셀 #101 (구간 1) 와 id 중복" },
            { "id": 102, "outcome": "remapped", "new_id": 131 } ],
  "warnings": ["셀 12 Z -3 ≤ 0 — …"]
}
```

`rows` 는 보낸 순서 그대로, `id` 는 **보낸 id**(`new_id` 가 옮긴 번호). `warnings` 는 막지 않은 것만
(바닥 Z ≤ 0, 덮어쓰기·구역 교체에서 무시한 충돌).

## 화면

레이아웃 편집 → 생성 규칙 탭:

- **추가 / 구역 교체 / 덮어쓰기** 토글과 **AutoId** 스위치(추가일 때만). 고른 값은 브라우저에 남는다.
- 규칙을 고칠 때마다 미리보기 한 줄(`추가 n · 갱신 k · 번호 변경 j · 건너뜀 m · 삭제 r`)과 건너뛸 칸의 사유.
- 맵의 생성 예정 칸은 판정별로 색이 다르다: 추가 = 주황 점선, 갱신 = 파랑, 건너뜀 = **경고색**(사유는 툴팁).
- 적용 버튼이 무엇을 할지 말한다(`추가 12칸 (건너뜀 2)` · `구역 교체 — 삭제 40 · 생성 44`).
- 적용 뒤에는 **서버가 돌려준** 줄별 결과가 그 아래에 남는다.

## 로컬 → PLC 두 단계

적용은 콘솔 DB 만 바꾼다. 편집 화면의 띠(`components/task/PlcWriteBar.tsx`)가 그 상태와 다음 조작을 낸다:

- 칩 `로컬 118 · PLC 미반영 37` — 마지막 PLC 읽기·쓰기 뒤로 고친 행 수(셀의 `dirty`). `?` 가 두 단계를 설명한다.
- **PLC 쓰기** 버튼이 적용 옆에 선다(표의 ⋯ 안에도 그대로 있다). 막히면 이유를 말한다 —
  쓸 행 없음 · 미반영 없음 · PLC 연결 끊김 · 쓰는 중.
- 확인 창에 **로컬 vs PLC 차이**(값 다름 · 로컬에만 · PLC에만 + 다른 Id 앞부분), 대상 PLC 선택(기억한다),
  쓰는 순서 안내, AUTO 모드 강제 쓰기 체크.
- 성공하면 `GR2 · 셀 37건 반영 · 검증 OK` 토스트 + 목록 재조회(미반영 표시가 사라진다).
  검증이 어긋나면 상태를 그대로 두고 오프셋과 **아직 다른 id** 를 알려 준다.

PLC 에 **무엇을 쓰는지는 바뀌지 않았다** — 배열을 Id 순으로, 남은 슬롯 0, `Count` 마지막, 되읽기 검증,
슬롯 규칙 `id % 100`, AUTO 가드 모두 백엔드 그대로다(`registry::plc_io`).

스테이션에는 일괄 쓰기(지우고 새로 까는 길)가 없다 — 그리드에서 **사람이 지운 행만** 삭제된다.
같은 PLC 쓰기 띠는 스테이션 탭에도 선다.
