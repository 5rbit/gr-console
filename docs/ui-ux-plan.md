# UI/UX 개선 — 리서치와 결정 기록

`docs/DESIGN.md`가 **지금의 규칙**이고, 이 문서는 **왜 그 규칙이 됐나**다. 규칙을 바꿀 때 여기에
줄을 더한다(지우지 않는다 — 버린 선택지의 이유가 다음 사람의 시간을 아낀다).

- 대상: `apps/gr-web` 셸
- 요구: ① 다기종 로봇 제어기 + 개발 툴에 맞는 셸, **창을 사용자가 자유롭게 구성** ② 간단하고 일관된
  사용성, **데이터 위주의 뷰** ③ 작업 도구(유니티 · VSCode) 리서치 후 적용

---

## 1. 무엇이 문제였나

개선 전 셸은 **메뉴바 + 고정 왼쪽 사이드바 + 화면 하나 + 상태바**였고, 화면 넷(작업 명령 · Task
관리 · 측정 모니터 · 시나리오)을 탭으로 갈아 끼웠다.

1. **왕복이 전부 탭 전환이다.** 명령을 내고 결과를 보려면 `작업 명령` → `Task 관리`로 화면을 떠나야
   하고, 돌아오면 작성 중이던 맥락이 사라진다. 엔지니어링 콘솔의 실제 일은 명령 → 결과 → 값의
   **왕복**인데 셸이 그 왕복을 화면 전환으로 만들었다.
2. **보조 면을 옮길 수 없다.** 로봇·PLC·상태 세 목록이 `Sidebar.tsx` 안에 코드째 박혀 있어 오른쪽에
   붙이거나 접거나 하단으로 내릴 수 없었다. 벽 모니터와 노트북이 같은 배치를 강요받는다.
3. **일관성의 축이 화면마다 갈렸다.** 밀도 스위치가 사이드바 안에만 있었다(`gr-sidebar-dense`) —
   "좁게 보기"가 사이드바에만 적용되고 표에는 적용되지 않는다.
4. **규칙이 문서가 아니라 주석에 흩어져 있었다.** `CLAUDE.md`도 스킬도 없어서, 화면별 담당
   에이전트가 각자 다른 규칙으로 UI를 늘렸다. → 그래서 이번 작업의 1번 산출물이 `docs/DESIGN.md`다.

## 2. 리서치 — 유니티 · VSCode

### 가져온 것

| 출처 | 가져온 것 | 왜 |
| --- | --- | --- |
| VSCode `Part` 격자(사이드바·패널·에디터 그룹을 Layout이 배치) | 존 넷(왼쪽·중앙·오른쪽·하단) 도킹 | 명령·결과·값이 한 화면에 선다 |

| VSCode 명령 팔레트 | `⌘/Ctrl+K`·`⌘⇧P`, "메뉴에 있는 것은 팔레트에도 있다" | 조작이 늘어도 메뉴가 창고가 되지 않는다 |
| VSCode `Customize Layout`(Default/Compact) | 전역 밀도 한 축 | 밀도는 화면의 성질이 아니라 읽는 사람의 성질 |
| VSCode `View: Reset View Locations` | `배치 초기화` | 자유 배치에는 **되돌아올 자리**가 반드시 있어야 한다 |
| VSCode 탭 드롭 위치(왼쪽 절반/오른쪽 절반) | 탭 삽입 지점 계산 | 이미 몸에 익은 감각을 새로 배우게 하지 않는다 |

| Unity 도킹 창의 창 메뉴(maximize·close 등) | 탭 우클릭 / `⋮` 메뉴 | 드래그를 못 쓰는 환경(터치 모니터·장갑)의 유일한 이동 수단 |
| Unity UX Essentials — 빈 창 대신 빈 상태, 비활성 컨트롤은 **이유**를 말한다, 조작 라벨은 동사 | `EmptyState`·`disabled` 사유·라벨 규칙 | 기존 규칙(조작/표시 분리)과 같은 방향이라 바로 얹혔다 |
| Unity 최소 폭 강제(Inspector 275px) | `ZONE_LIMITS`의 존별 min/max | 줄일 수 있는 폭에는 **읽을 수 없는 폭**이 포함되면 안 된다 |

### 버린 것 — 그리고 그 이유

| 버린 것 | 이유 |
| --- | --- |
| **OS 창으로 떼기(pop-out)** — 유니티·VSCode의 Floating Window | 단일 PLC 문맥이라 떼어 낼 만큼 독립적인 창이 없다. 벽 모니터에서 떼어 낸 창은 유실된다. 브라우저에서는 별 window라 스토어·SSE가 갈리고, **값이 두 창에서 다르게 보이는 것**이 이 콘솔에서 가장 나쁜 버그다 |
| **자유 좌표 플로팅** | 겹친 창은 가려진 값을 만들고, 가려진 값은 없는 값보다 나쁘다 |
| **중앙 좌우 분할(에디터 그룹 여러 개)** | 지금은 하단 존이 그 일을 한다. 넣기 전에 "무엇을 나란히 보는가"의 실사용 예가 필요하다(백로그) |
| **Zen 모드** | 최대화(`Alt+Enter`)가 같은 필요를 채우고, 상태바를 숨기는 것은 이 콘솔에서 위험하다(알람이 상태바에 있다) |
| **탭 고정(Pin)** | 탭이 패널당 하나뿐(최대 일곱)이라 고정으로 아낄 것이 없다 |
| **다중 창 레이아웃을 서버에 저장** | 배치는 "그 사람 그 모니터"의 성질이다. 같은 계정이 24인치와 벽 모니터를 오가며 같은 배치를 강요받으면 매번 다시 짠다 → localStorage + 이름 붙인 저장 |

### 설계 결정 몇 가지 (왜 그렇게)

- **불변식을 `normalize()` 하나로.** 레이아웃을 바꾸는 길이 넷(드래그·프리셋·복원·팔레트)이라, 규칙을
  각 경로에 두면 한 곳만 빠뜨려도 "탭은 있는데 아무것도 안 그려지는" 화면이 난다.
- **`lib/workspace`는 패널 id만 안다.** lib이 화면을 import하면 순수 모델 테스트가 React를 끌고 온다.
  경계는 `components/workspace/paneRegistry.tsx`.
- **비활성 탭 언마운트.** 화면 넷이 동시에 살면 SSE·폴이 넷 다 돈다. `renderedPanes()`가 그 규칙을
  계산하고, 최대화도 "존 하나만 그린다"로 구현했다(`display:none`이 아니라).
- **머리띠 요약을 컴포넌트로 export.** 함수로 내면 껍데기가 그 스토어를 구독하지 않아 숫자가 굳는다.
- **`nav.tab` ↔ 중앙 활성 탭 양방향 동기화.** 다른 화면의 `nav.goTask(id)`가 도킹 모드에서도 그
  패널을 드러내야 하고(숨은 탭이면 눌러도 아무 일도 없는 것처럼 보인다), 사용자가 중앙 탭을 바꾸면
  `?tab=` 딥링크가 따라와야 한다. 서로를 다시 부르지 않도록 **마지막으로 본 값**으로 누가 먼저
  움직였는지를 가른다(`WorkspaceShell`).
- **밀도는 CSS 변수로.** 컨트롤 높이 토큰만 갈아 끼우고 킷이 그 토큰으로 높이를 부르게 했다 —
  그러면 화면은 손대지 않아도 따라온다(그 대가로 킷의 하드코드 높이를 한 번 걷어 냈다. 아래
  '가이드로 대조하면서 찾은 것' 2번). 글자 크기는 건드리지 않는다(11px 아래는 오독).

### 가이드로 대조하면서 찾은 것 둘

`docs/DESIGN.md`를 먼저 쓰고 그 규칙으로 이번 코드를 훑었더니 **문서가 코드의 거짓말을 두 개
잡았다**. 이것이 가이드를 먼저 쓴 값이다.

1. **좁은 존에서 `ScreenHeader`가 글자 중간에서 끊겼다.** 화면이 도킹 존(오른쪽 200~560px)에 들어갈
   수 있게 되면서 요약 항목이 줄바꿈되며 `실 행 0`이 됐다. 끊긴 값은 안 보이는 값보다 나쁘다 —
   읽을 수 있다고 착각하게 만든다. → 컨테이너 쿼리로 32rem 미만이면 요약을 접는다(제목·조작이 먼저).
   미디어 쿼리가 아닌 이유: 기준이 창 폭이 아니라 **그 띠가 든 존의 폭**이다.
2. **밀도의 실제 효력이 문서가 주장한 것보다 훨씬 작았다.** 컨트롤 높이 토큰을 쓰는 자리가 셋뿐이고
   `h-7`/`h-8`/`h-9` 하드코드가 33곳이었다 — 밀도를 켜도 킷 절반이 제 높이로 남아 줄이 어긋났다.
   → 킷의 높이를 토큰으로 바꿨다(`Button`·`Input`·`Select`·`Switch`·`Segmented`·`IconPopover`·
   `ScreenHeader`·`Toolbar` + 셸 메뉴바·탭 띠). 측정: 메뉴바 36→30 · 머리띠 36→30 · 컨트롤 32→28 ·
   상태바 24→24(일부러 안 줄인다). 문서를 코드에 맞춰 낮추는 대신 **코드를 문서에 맞춰 올렸다**.

### UX 전반 점검 — 평가와 고친 것

실제 앱을 브라우저로 몰아 보며 셸을 평가했다. 나온 문제 여섯과 처리:

| # | 평가 | 고친 것 |
| --- | --- | --- |
| 1 | **제목이 두 번 나왔다** — 탭이 `Task 관리`를 말하고 그 아래 머리띠가 또 말했다. 30px을 정보 없이 먹는다 | 껍데기가 문맥으로 "이름은 내가 말했다"를 선언하고 `ScreenHeader`가 제목을 접는다(`lib/ui/paneChrome.ts`). 요약·조작만 남고, 남을 것이 없으면 띠 자체가 사라진다. 화면 코드는 손대지 않았다 |
| 2 | **창 경계가 안 보였다** — 스플리터가 hover 전에는 투명해서 "끌 수 있다"도, 면이 갈리는 자리도 화면에 없었다 | 선을 항상 1px로 보이게 하고 hover에서 3px·초록으로. 경계가 곧 크기 손잡이라는 것이 보인다 |
| 3 | **어느 패널이 활성인지 몰랐다** — `Alt+Enter`가 늘 중앙을 최대화했다. 오른쪽을 보다 눌러도 중앙이 커진다 | `workspace.focused`(마지막으로 만진 패널)를 도입. 창 명령의 대상이 되고, 활성 존의 탭 띠가 밝아지고 그 탭만 accent 밑줄을 받는다(다른 존은 회색 밑줄) |
| 4 | **빈 존이 사라져 도킹의 막다른 길이 생겼다** — 패널이 하나도 없는 존은 화면에서 없어져서, 탭을 끌어도 놓을 자리가 없었다(창 메뉴만이 길) | 드래그 중에는 빈 존도 점선 레일로 뜬다. 놓을 수 있는 자리는 끌고 있는 동안 보인다 |
| 5 | **토글 관용구가 갈렸다** — 메뉴는 체크박스, 팔레트는 `접기`/`펼치기`로 라벨이 뒤집혔다 | 팔레트도 체크로 통일(`왼쪽 존` + 체크). 같은 항목을 두 이름으로 배우지 않는다 |
| 6 | **닫기(✕)가 hover에만 있었고, 닫힐 수 없는 탭에도 있었다** | 활성 탭의 ✕는 늘 보인다(hover-only는 없는 기능이다). 중앙의 마지막 탭에는 ✕를 그리지 않는다 — 눌러도 아무 일 없는 버튼은 고장으로 읽힌다. 최대화 중에는 탭 띠에 `해제` 버튼이 선다(나가는 길은 화면에) |

### 테스트

순수 모듈만 테스트한다(기존 규약). 새로 64건: `model.test.ts` 50 · `commands.test.ts` 14.
불변식(중앙은 비지 않는다 · 중복 탭 · 활성 탭 보정 · 모르는 id 제거 · 크기 클램프 · 깨진 저장값)이
전부 테스트로 못 박혀 있다.

## 4. 다음 단계 (백로그)

1. **중앙 좌우 분할** — 두 작업면을 나란히. "무엇을 나란히 보는가"의 실사용 예가 모이면.
2. **패널별 상태의 URL 직렬화** — 지금 `?tab=`은 활성 화면만 싣는다. 필터·선택 행까지 실으면 배치와
   맥락을 링크 하나로 공유할 수 있다(현장 인수인계에 쓰인다).

   (localStorage는 그 사람 그 브라우저에 갇혀 있다).
